# `match/` 匹配

多路召回的编排、融合与排序。不截断——截断是 `curate/` 在预算约束下的决定。

**依赖**：`vector/`、`lexical/`、`lsp/`、`model/`、`store/`
**被依赖**：`curate/`

## 输入输出

```
输入   自然语言任务描述 + 分支 + dirty overlay + 预算
输出   约 200 条排序后候选
```

## 查询理解——当前空白

**本模块最前面应该有一层，目前完全没有。**

agent 传来的自然语言直接拿去嵌入和 BM25。但：

- 要不要查询改写 / 扩展？
- 要不要拆子查询分别召回？
- HyDE（先生成假想答案再嵌入）值不值得？

`lexical/` 尤其受影响——「为什么加载 yaml 会崩」里没有一个词会出现在 `ConfigParser::parse` 里。

这是阻塞项，见 [`../open-questions.md`](../open-questions.md) C1。

## 三路召回

单路都有确定的盲区：

| 路径 | 找得到 | 找不到 |
|---|---|---|
| `vector/` | 语义相近的代码 | 写得干净但无注释的函数 |
| `lexical/` | 错误字符串、日志、配置键、标识符 | 不含查询词但逻辑相关的代码 |
| `lsp/` | 调用链上的邻接代码 | 未 checkout 分支上的一切 |

三路互相兜底。任何一路单独使用都会系统性漏召回。

### 为什么符号那一路不能省

纯向量跟不动多跳引用链。`handler` → `auth` → `jwt` 三个文件语义上一点都不像。

Augment 公开的案例：Ansible BCrypt 修复要跨多层改动，文本搜索找到顶层 API，符号关系找到测试实际调用的底层工具函数。

他们为此训练专门的嵌入模型来弥补，因为要在纯向量框架里解决图问题。本项目不需要——关系是现成的。

## 分支过滤

每一路按分数流式交出候选，本模块逐条做分支可见性测试，凑满 200 条可见的为止。降权（见下）只会压低分数，所以当已留下 200 条、而下一条的原始分数不高于第 200 名的降权后分数时，后面的候选不可能再进来，读取到此为止。

不用固定倍数过取：一个热点函数被改过多次，它的多个版本会挤满排序前列，而查询分支上只有其中一个可见。

可见性按 `store.md` 的查找链判定：Chunk → blob → 文件版本 → 分支位图。同一次查找顺带给出路径与行号。任意分支包含全部 Chunk 的绝大部分，选择性极高，所以后过滤比 filtered HNSW 更合适。

## 测试代码降权

测试文件里的候选分数乘以 0.5，仍然留在结果里。测试文件按路径约定识别（`ingest/` 的 `is_test`：`tests/`、`src/integTest/` 这类目录，`foo_test.go`、`test_foo.py`、`FooTests.java`、`foo.spec.ts` 这类文件名）。

任务描述问的是行为在哪里实现，而复现这个行为的测试和描述几乎逐词相同，按原始分数会排到实现前面。不排除：agent 写修复时常常需要读测试。

## 文件级排名

两个排名用 RRF（k = 60）融合：

| 排名 | 依据 | 擅长 | 盲区 |
|---|---|---|---|
| 按 Chunk | 文件中最高的 Chunk 分 | 精确：一个函数高度吻合就上来 | 证据分散在大文件多个函数里时排不上去 |
| 按整文件 | 整个文件作为一篇 BM25 文档 | 大文件里分散的证据会累加 | 被一次命中很多词的长文件带偏 |

两个分数量纲不同，只按名次融合。不用 Chunk 分求和代替整文件排名：求和的结果随候选数大幅摆动（D21）。

## Chunk 排名

每个 Chunk 的名次与它所在文件（取最好的那个）的融合名次再做一次 RRF。先定位文件、再定位函数：一个函数单看分数不突出，但它所在的文件排在前面，它就更可能是要改的地方。

### 评测需要 commit 级可见集

**Branch** 的定义是分支当前 tip，但 [`../benchmark.md`](../benchmark.md) 的铁律二要求每条 query 在它自己的 PR base commit 快照上检索——这是本模块现在没有的粒度。

不为此新增概念：评测期把每个 base commit 注册成一个伪 **Branch**（`eval/<repo>/pr-<n>`），复用同一套 bitmap。bitmap 数量等于 query 数（≤ 2,800），稀疏，代价可忽略。

这是跑 L1 的前置，阶段 1 做掉。

## dirty overlay 合并

客户端上传的未提交文件，经 `model/` 临时嵌入后并入候选池，**不进 `vector/` 的全局索引、不落盘**。

量很小（通常个位数文件），线性扫描后合并。不要为几十个 Chunk 实现动态索引插入——那是用大量复杂度换毫秒级收益。

## 融合

三路的分数不可直接比较：余弦相似度、BM25 分数、图距离，量纲完全不同。

**RRF（Reciprocal Rank Fusion）是默认选择**——只用名次不用分数，天然免疫量纲问题。

权重怎么定、要不要按查询类型动态调整，未决。见 [`../open-questions.md`](../open-questions.md) C2。

## 重排

调 `model/` 的 `jina-reranker-v3.5`。131K 合并上下文，150 个候选一次塞完。

listwise——所有候选一起评估再排序，优于 pairwise cross-encoder。

公开数据：重排给 NDCG 带来 +68%（稀疏）到 +120%（稠密）的提升。**单位工作量收益最高的一环。**

## 输出量：约 200 条，不是 5 条

**本模块的职责是排序，不是截断。**

一个高度相关但 800 行的函数，和一个中度相关但签名只要 30 token 的函数——谁进最终结果取决于预算，而本模块不掌握预算信息。

如果这里收窄到 5 条，`curate/` 就没有任何可优化的余地。

200 而不是 50：类的剩余部分等非函数块同样占名额，50 条时函数级 Recall@50 被名额本身卡住（D21）。

## 跨进程执行

`lsp/` 在客户端，其余在服务端，所以本模块的召回是跨进程的两阶段：

```
① 服务端：vector/ + lexical/ 召回 + 分支过滤
② 客户端：lsp/ 符号扩散
③ 服务端：融合 + 重排
```

详见 [`serve.md`](serve.md)。
