# `curate/` 策展

**与开源同类方案差距最大的模块，也是最容易被跳过的。**

处理单次调用内的组装。跨会话累积的知识在 [`playbook.md`](playbook.md)。

**依赖**：`match/`、`parse/`（签名提取）、`playbook/`
**被依赖**：`serve/`

## 输入输出

```
输入   约 50 条排序后候选 + token 预算 + 会话标识
输出   一个 Context Package
```

## 它解决什么

`match/` 解决「哪些代码相关」。本模块解决「在有限预算里，放哪些、各放多长」。

这两件事不同。一个函数高度相关但有 800 行；另一个中度相关但签名加注释只要 30 token。在 8000 token 预算下，正确答案往往是后者加上前者的签名。

## 为什么它是差异化所在

Augment Context Engine 在 Terminal Bench 2.0 上相对 Claude Code：token 少 32%、花费低 33%、**准确率打平**。

准确率打平说明召回质量没有赢。省下的 32% 全部来自不返回无用内容——那是本模块的贡献。

**`ingest/` 到 `match/` 决定质量上限，`curate/` 决定单位 token 的信息密度。**

没有本模块，整个系统就是一个检索器，不是上下文引擎。

## 多级保真

| 档位 | 内容 | 典型开销 | 来源 |
|---|---|---|---|
| 全文 | 完整代码 | 数百至数千 token | `store/` |
| 签名 | 函数签名 + 文档注释 | 20–60 token | `parse/` |
| 摘要 | 一句话说明 | 15–30 token | 离线摘要 |
| 引用 | `path:line` | 5–10 token | `store/` |

### 压缩用语法树，不用模型

签名档和引用档由 `parse/` 直接产出：确定性、零成本、零延迟。

**在查询路径上调模型做压缩，要为每次检索付钱和付延迟，方向错误。**

摘要档只用于已有离线摘要的对象（提交记录、Playbook 条目），不在查询时现算。

## 预算分配

给定预算和排序后候选，选一个子集并为每条选一个保真档，使总信息量最大。

本质是背包问题，但**不需要最优解**。按名次贪心加多样性约束能拿到大部分收益。

关键性质：**降档而不是丢弃。** 排名靠后的候选降到签名档或引用档仍然进包——agent 至少知道它存在，可以通过 `expand` 要回原文。

## 去冗

同一段代码可能经三路召回重复出现；一个方法和它所属的类内容重叠；复制粘贴的工具函数近似重复。

必须在组装前合并，否则预算被同一份内容吃掉多次。

## 多样性

五条结果全部来自同一个文件是常见失败形态。

MMR（Maximal Marginal Relevance）在相关性和新颖性之间取平衡，避免预算被单一区域吃光。

权衡系数未定，见 [`../open-questions.md`](../open-questions.md) C4。

## 与 `playbook/` 的汇合

Playbook 条目和代码 Chunk 在不同的向量空间里检索，**在本模块才汇合**。

跨会话重复命中的 Chunk 被替换为相关条目加引用，而不是原文重发，也不是略去。详见 [`playbook.md`](playbook.md)。

## 评价

**不是 Recall@K。**

验收标准是「相同质量下的 token 用量」，对标 Augment 的口径。

在自建测试集的 **L3** 上扫预算曲线：固定 L1 Recall@10 / L2 Recall@50 达标，测 Context Package 的实际 token 数。

| 预算 | L1 Recall@10 | L2 Recall@50 |
|---|---|---|
| 2K | | |
| 4K | | |
| 8K | | |
| 16K | | |
| 无限 | | |

**在哪个预算点达到无限预算档的质量，那个点越低本模块越有效。**

每次报分必须同时给出 ripgrep 与 BM25 两条免费基线，否则分数无法解释。

详见 [`../benchmark.md`](../benchmark.md)。
