# `vector/` 向量库

近似最近邻检索。只答自己这一路，不做多路协调。

**依赖**：usearch（或 hnswlib）、`store/`
**被依赖**：`match/`、`playbook/`

## 选型

**usearch**，C++ header-only，支持 int8 量化。

备选 hnswlib（更简单，无量化）。

### 明确避开 `sqlite-vec`

v0.1.10-alpha，只支持 f32，无量化，无 SIMD。本项目要存百万级向量并量化，它做不到。

## 索引形态：一个全局 HNSW

**不为每个分支建独立索引。**

关键观察：任意分支包含全部 Chunk 的绝大部分。选择性极高，所以过取加后过滤优于 filtered HNSW——后者在低选择性下严重退化，而这里根本不是低选择性场景。

```
ANN 取 top-k（k = 1000，不够则 4000、16000）
  ↓
交给 match/ 做分支可见性测试
  ↓
两组各满 200 就停，否则加大 k 重查
```

不用固定过取倍数（D24）：热点函数的多个版本会挤满排序前列，而查询分支上只有其中一个可见，倍数取多少都是猜。

过滤本身不在本模块——本模块只负责「给我 top-K」，分支语义与重查循环属于 `match/`。

副作用：切换分支等于换一个 bitmap 指针；新建分支等于拷贝 bitmap 再应用 diff。两者都不触发本模块重建。

## 维度与精度

维度 **1024**（D7）。理由是 Jina v4 与 voyage-code-4 的交集，切换 Provider 时存储布局不变。

落盘精度 **fp32**（D22），索引精度也取 **f32**（D24 实测）。

i8 索引小 3.2–3.6 倍、建索引快一倍，`recall@10` 几乎不变，但名次指标掉 9–16%（file_mrr 0.451 对 0.533）——量化重洗了近似并列的候选，而 `curate/` 在预算内吃的正是名次。i8 留给索引装不下的场合：1024 维 140 万块，f32 约 5.6 GB、i8 约 1.4 GB，那个规模上要重测。见 [`../open-questions.md`](../open-questions.md) C7。

## HNSW 参数

`M = 16`、`efConstruction = 128`、存储精度 **f32**（实测，D24）。

**`efSearch` 这个旋钮不存在，已删掉**：usearch 的搜索用 `max(efSearch, wanted)`，而本模块的 `wanted` 是过取量（起步 1000），任何低于过取量的值不起作用；实测高于过取量也买不到增益，调到 16000 反而掉分（D24）。过取量就是搜索扩展量。

扫参数据见 D24。**扫参不重嵌**，从已存的向量重建索引即可，零额外成本。见 [`../open-questions.md`](../open-questions.md) C5。

## 索引是派生缓存（D24）

唯一真值是 `chunks.embedding`（fp32，L2 归一化）。索引落在 `<db>.usearch`，删了能重建，参数变了重建，碎片了重建。

- key 是 `chunk_id`，不建映射表
- 重建由 `realontext build-index` 显式触发，全量
- 索引记录建库时的向量数与最大 `chunk_id`，与库不符时查询路径报错并提示重建，不静默出错
- **不进 `embed.*` 指纹**：指纹保护付过费的向量，派生物重建零成本

增量删除不做——GC 是阶段 10，那时全量重建。

## 另一个索引：Playbook 条目

`playbook/` 的条目也走本模块，与代码 Chunk 同一套嵌入和检索机制，但**是独立的索引实例**——条目和代码不在同一个向量空间里做排序，它们在 `curate/` 层才汇合。

条目的语义去重也用本模块（ACE 的 grow-and-refine 依赖嵌入相似度）。
