# `playbook/` 知识库

策展的持久化部分，也是 D17 的答案。

[`curate.md`](curate.md) 讲单次调用内的组装，本文件讲跨会话累积的知识。

**依赖**：`store/`、`model/`、`vector/`
**被依赖**：`curate/`

## 它解决的问题

会话级去冗有一个无法回避的失效模式：

```
第 1 次检索   引擎返回 auth.cpp 全文，记账「已给过」
              ↓
agent 会话变长，触发上下文压缩，auth.cpp 被丢弃
              ↓
第 5 次检索   引擎查记账，判定「给过了」，略去
              ↓
agent 从未看到它需要的代码，且不知道它存在
```

静默、不报错、agent 无从察觉，而且会话越长越容易触发。

**根因是引擎在对一份自己不拥有的状态做假设。** agent 的上下文由 agent 管理，引擎看不见。

## 解法：不靠扣留去冗，靠蒸馏去冗

引擎不记录「我发过哪些 chunk」，而是维护一份关于这个仓库的**持久知识库**。

重复命中时返回的不是「什么都没有」，而是**提炼后的条目加引用**：

```
第 1 次    auth.cpp:40-88  [全文 620 token]

第 5 次    · token 过期校验在 validate_token()，auth.cpp:40-88
           · 已知坑：过期判断用 < 而非 <=，边界值会漏
           · 相关变更：2026-03 的 commit a3f9c1 修过一次同类问题
           [约 60 token，且信息量高于原文]
```

**永不扣留，只做替换。** 失败模式从「静默丢失」变成「给了一个更浓缩的版本」——后者即使不理想也是可恢复的，agent 看到引用就知道原文存在，可以要回去。

这同时解决了省 token 和不丢信息的冲突：条目比原文短一个数量级，但因为它是提炼过的，单位 token 信息密度更高。

## 设计来源

[ACE 论文](https://arxiv.org/abs/2510.04618)（Agentic Context Engineering，Stanford + UC Berkeley + SambaNova，ICLR 2026，[开源实现](https://github.com/ace-agent/ace)）。

与 Augment Context Engine 撞名，是两个不同的东西：Augment 是商业产品，ACE 论文是方法。本项目的知识库层采用论文的方法。

论文的核心论点一句话：

> 上下文不该变得更短，该变得组织更好。

## 数据结构

知识库是一份 **playbook**，由**条目（bullet）**组成。每个条目：

| 字段 | 内容 |
|---|---|
| `id` | 唯一标识，稳定 |
| `content` | 一条可复用的策略、领域概念或失败模式 |
| `helpful` | 被判定有用的计数 |
| `harmful` | 被判定有害的计数 |
| `embedding` | 用于检索和去重 |
| `refs` | 关联的 chunk / commit / 符号 |

条目是**扁平的、可独立寻址的**，不是一篇文章。这是能做增量更新和细粒度检索的前提。

## 三个角色

论文的分工：

| 角色 | 职责 | 在本项目中 |
|---|---|---|
| **Generator** | 产生推理轨迹，暴露有效策略和反复出现的坑 | **就是 agent 自己**，我们不运行它；我们记录检索轨迹 |
| **Reflector** | 批判轨迹，提炼教训，可多轮迭代 | 服务端离线批处理作业 |
| **Curator** | 把教训合成紧凑的 delta 条目，确定性合并 | 服务端离线批处理作业 |

关键点：**Reflector 和 Curator 不在查询路径上。** 它们是离线作业，跑在 DeepSeek 谷时窗口，和 commit 摘要共用同一套队列、调度器和重试逻辑（见 [`ingest.md`](ingest.md)）。

查询路径只读知识库，不写。

## 增量更新（delta update）

**不做整体重写。** Reflector 产出候选条目，Curator 把它们合并进 playbook。

论文对整体重写的批判有具体数据：一次单步的整体重写把上下文从 **18,282 token（准确率 66.7%）压缩到 122 token（准确率 57.1%）**。

这个现象叫 **context collapse**——反复重写会持续侵蚀细节。增量更新从机制上杜绝它。

另一个相关的病叫 **brevity bias**：优化目标偏向简洁的方法会丢掉领域特有的启发式规则，而复杂任务恰恰依赖这些。

对本项目的含义：**知识库允许变大。** 不要为了「保持简洁」定期总结压缩它——那正是论文测出会掉分的做法。

## grow-and-refine

- 新条目**追加**
- 已有条目**原地更新**（计数器递增），不重写
- 去重用**语义嵌入**——我们已经有嵌入管线，直接复用
- 去重时机：每次 delta 后主动做，或等窗口满了惰性做

计数器的作用是让条目有可证伪性。一条被反复标记 harmful 的条目应该被淘汰，而不是永远留着误导检索。

## 论文的效果数据

| 指标 | 结果 |
|---|---|
| AppWorld agent 任务 | 平均 +10.6% |
| Finance（FiNER + Formula） | 平均 +8.6% |
| 适配延迟 | 降低 82.3% |
| rollout 次数 | 减少 75.1% |

AppWorld 上用较小的开源模型达到了基于 GPT-4.1 的头部生产级 agent 的水平。

## 与已有模块的关系

本模块几乎不引入新依赖：

| 需要的能力 | 复用的模块 |
|---|---|
| 条目嵌入 | `model/` |
| 条目检索 | `vector/`（独立索引实例） |
| 语义去重 | `vector/` |
| 离线批处理队列与谷时调度 | `model/`，与提交摘要共用 |
| 廉价模型调用 | `model/` 的 DeepSeek |
| 持久存储 | `store/` 的 `bullets` 表 |

新增的只有：条目表、Reflector 提示词、Curator 合并逻辑。

## 存储位置

**服务端。**

不写进被索引的仓库。这与 grill-with-docs 的做法不同——后者把 `CONTEXT.md` 和 `docs/adr/` 写进用户的 git 仓库，作为用户资产接受 review。

本项目选服务端的理由：知识库是自动累积的机器产物，条目数量会到数千级，且带计数器等运行时元数据，不适合进 git diff。

**代价：** 用户无法直接 review 和修订知识库内容。需要提供导出和人工干预的接口，否则一条错误条目会永久污染检索结果。这一点见 [`../open-questions.md`](../open-questions.md)。
