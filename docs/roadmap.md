## 阶段 0：建测试集（不可跳过，且零成本）

**自建测试集，不用公开基准验收**（D20）。三条铁律与完整方法见 `benchmark.md`。

- **先数再抓**：14 个仓库各出一个「满足全部过滤条件的 PR 数」。「每仓库 100–200 query」目前是估的，某个语言只剩二十条，「七种语言权重相同」这个前提就不成立
- 按 `../eval/repos.txt` 的 14 个仓库抓 merged PR 与其关联 issue
- 建时间锚定语料：每个 query 对应仓库在该 PR base commit 时刻的状态
- 应用过滤规则，冻结 PR 列表进 git
- 冻结**评分规则**：命中判据、限定名归一化表、两条基线的完整构造、报分模板。规则留空等于把打分权交回给出卷人
- 建 **ripgrep** 与 **BM25** 两条基线，两者都不许 import 本项目代码
- 报「query 里直接出现 ground truth 标识符的比例」，确认测试集没退化成字符串匹配

**全程纯 git + GitHub API，零 API 模型调用，零成本。**

装置已建：[`../eval/`](../eval/README.md)，`.github/workflows/eval.yml` 手动触发，`size` 输入切中等档 / 超大档。向量基线跑本地 Jina 权重，同样不花钱。

本阶段的产出不是一个绝对分数，是**两条免费基线的数值**。后续每个阶段都必须同时报这两条——分数涨而基线同步涨，说明测试集变简单了，不是系统变好了。

**后续任何实现打不过 ripgrep 基线就停下来查原因，不要继续加功能。**

原方案（commit message 当 query、patch 文件当答案）已废弃：既有数据泄漏，查询分布也错。理由见 `benchmark.md`。

## 阶段 1：拉取、内容寻址与 BM25 召回

- libgit2 裸镜像拉取
- `git for-each-ref` 枚举全部分支
- tree-sitter 切块
- **内容寻址去重**（blob_sha → chunk 缓存），分支位图按文件版本编号（`modules/store.md`）
- SQLite FTS5 BM25，代码分词器（`modules/lexical.md`）
- **base commit 注册为伪 Branch**，给评测提供 commit 级可见集（`modules/match.md`）
- CLI：`index` / `query`。不做 MCP

去重前置的原因：它现在是成本基础设施，不是优化项。没有它，多分支索引在经济上不成立（$600 vs $31）。

BM25 放在这一阶段的原因见 D21：它零成本，让 `store/` 的每张表在付费嵌入之前就有读者和分数。

**跑 L1（train）。文件级与函数级 Recall@10 都必须超过 BM25 基线。输一项就停。**

## 阶段 2：嵌入接入

- Jina API 客户端
- 双令牌桶限流（RPM + TPM）
- 指数退避重试，失败队列持久化
- 运行时 token 计数器

指纹校验必须在这一阶段做掉，不能等到真要切 provider 时再补——那时候已经有脏索引了。

## 阶段 6：`curate/` 策展

**这是本项目区别于「又一个代码检索器」的地方，不是可选增强（D16）。**

- 工具契约加入 `token_budget` 和 `session_id`
- 多级保真：tree-sitter 提取签名档与引用档
- 单次调用内去冗（三路召回的重复、方法与所属类的重叠）
- MMR 多样性约束
- 预算约束下的贪心组装
- 会话级去冗（策略见 D17）

前置要求：`match/` 的输出量要为本层留出选择空间，`match/` 交出约 200 条而非 5 条。

验收走 `benchmark.md` 的 **L3 预算曲线**：固定 L1 Recall@10 达标，测 Context Package 的实际 token 数，扫 2K / 4K / 8K / 16K / 无限。

**在哪个预算点达到无限预算档的质量，那个点越低本层越有效。**

不是 Recall@10。Augment 在这一层拿到的是 token 少 32%、准确率打平——赢的是单位 token 的信息密度，不是召回。

本阶段零额外成本，复用阶段 3 的嵌入。

## 阶段 7：`lsp/` 符号扩散

- LSP 客户端：`initialize` / `didOpen` / `definition` / `references` / `documentSymbol`
- server 生命周期与就绪探测
- 每语言启动配置表
- 候选符号扩一跳后并入 `match/` 的重排

**先用测试集证明增益再做。** 挂上 Serena 手工比对，测出符号信号在测试仓库上值多少分。值就自实现，不值就永远依赖外部工具。

本阶段同时解锁 **L2**——L2 的 ground truth 需要 language server 算一跳调用邻居，在此之前跑不了。

前面几轮把符号图当必需品，那个结论来自 Augment 的营销材料和一篇论文，不是来自你的仓库。

## 风险

| 风险 | 等级 | 说明 |
|---|---|---|
| `curate/` 策展没有成熟参照 | 高 | 闭源，无公开实现可抄。评价指标已在 `benchmark.md` L3 定义，但无人验证过它测的对不对 |
| 知识库计数器无信号源 | 高 | 阻塞阶段 8，见 `open-questions.md` A1 |
| 查询理解层完全空白 | 高 | `match/` 之前的一层，从未建模，见 C1 |
| 自建测试集出卷答题同源 | 高 | query、答案、调参在同一人手里。靠冻结 + holdout + 三条免费基线补偿，见 `benchmark.md` |
| 无外部可比数字 | 中 | 放弃公开基准的直接代价。不能声称 SOTA，只能声称相对 ripgrep / BM25 的增益 |
| Language Server 生命周期管理 | 中 | 崩溃重启、就绪探测、多语言配置表 |
| 打不过 ripgrep 基线 | 高 | 阶段 0 建基线，阶段 3 起每次报分都对照 |
| jina-embeddings-v4 代码质量不足 | 中 | 备选 voyage-code-4，但贵 6.7 倍，需在测试集上实测 |
| 首次索引耗时 | 低 | 一次性成本，可断点续传 |
| HNSW 增量删除碎片 | 低 | GC 时顺带重建 |
