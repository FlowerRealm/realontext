## 阶段 0：建测试集（不可跳过，且零成本）

**自建测试集，不用公开基准验收**（D20）。三条铁律与完整方法见 `benchmark.md`。

- **先数再抓**：14 个仓库各出一个「满足全部过滤条件的 PR 数」。「每仓库 100–200 query」目前是估的，某个语言只剩二十条，「七种语言权重相同」这个前提就不成立
- 按 `../eval/repos.txt` 的 14 个仓库抓 merged PR 与其关联 issue
- 建时间锚定语料：每个 query 对应仓库在该 PR base commit 时刻的状态
- 应用过滤规则，冻结 PR 列表进 git
- 冻结**评分规则**：命中判据、限定名归一化表、两条基线的完整构造、报分模板。规则留空等于把打分权交回给出卷人
- 建 **ripgrep** 与 **BM25** 两条基线，两者都不许 import 本项目代码
- 报「query 里直接出现 ground truth 标识符的比例」，确认测试集没退化成字符串匹配

**全程纯 git + GitHub API，零 API 模型调用，零成本。**

装置已建：[`../eval/`](../eval/README.md)，`.github/workflows/eval.yml` 手动触发，`size` 输入切中等档 / 超大档。向量基线跑本地 Jina 权重，同样不花钱。

本阶段的产出不是一个绝对分数，是**两条免费基线的数值**。后续每个阶段都必须同时报这两条——分数涨而基线同步涨，说明测试集变简单了，不是系统变好了。

**后续任何实现打不过 ripgrep 基线就停下来查原因，不要继续加功能。**

原方案（commit message 当 query、patch 文件当答案）已废弃：既有数据泄漏，查询分布也错。理由见 `benchmark.md`。

## 阶段 1：拉取、内容寻址与 BM25 召回（完成，2026-09-16）

- libgit2 裸镜像拉取
- `git for-each-ref` 枚举全部分支
- tree-sitter 切块
- **内容寻址去重**（blob_sha → chunk 缓存），分支位图按文件版本编号（`modules/store.md`）
- SQLite FTS5 BM25，代码分词器（`modules/lexical.md`）
- **base commit 注册为伪 Branch**，给评测提供 commit 级可见集（`modules/match.md`）
- 测试代码降权、整文件 BM25 与 Chunk 排名的 RRF 融合（`modules/match.md`）
- CLI：`index` / `query` / `symbols`。不做 MCP

去重前置的原因：它现在是成本基础设施，不是优化项。没有它，多分支索引在经济上不成立（$600 vs $31）。

BM25 放在这一阶段的原因见 D21：它零成本，让 `store/` 的每张表在付费嵌入之前就有读者和分数。

**跑 L1（train）。文件级与函数级 Recall@10 都必须超过 BM25 基线。输一项就停。**

## 阶段 2：嵌入接入

设计见 D22。

- Jina API 客户端（`model/`），libcurl
- 双令牌桶限流（RPM + TPM），预扣后按实际计费 token 结算
- 指数退避重试；失败不需要持久化队列，`embedding IS NULL` 就是队列
- 运行时 token 计数器（`embed` 的进度输出）
- **索引指纹写入与校验**（endpoint / model / task / dim / max_bytes / input_version）
- 嵌入输入按字节截断，切块不动
- **精确余弦扫描读者**（`query --route vector`）：付费之后当场有分数，也是阶段 3 ANN 的召回真值
- 本地 Jina 兼容服务（`eval/embed_server.py`）：没有 key 时用开放权重模型跑通整条管线

指纹校验必须在这一阶段做掉，不能等到真要切 provider 时再补——那时候已经有脏索引了。

**验收**：

1. 单元测试：限流、重试分类、响应解析、指纹各项拒绝、失败后续跑、精确排序
2. 本地模型在小 train 仓库（先 tokio）上跑通 `index → embed → query --route vector`；中途 kill 后续跑，待嵌入数归零
3. 纯向量 L1 与 grep / bm25 并列报分，扫 `max_bytes` 定默认值。本阶段不要求打过 BM25，那是阶段 3 的门槛
4. 拿到 key 后：先验证 Jina v4 的请求格式（D22 未验证项），再付费嵌入

## 阶段 3：检索可用（完成，2026-09-17）

设计见 D24（向量索引形态）、D25（`serve/` 范围）。

- usearch 向量索引：全量重建的派生缓存，`chunk_id` 当 key
- **递增重查**代替固定倍数过取（1000 / 4000 / 16000，两组各满 200 就停）
- `--route ann` 与 `--route vector` 并存，精确扫描保留为召回真值
- HNSW 参数（C5）与量化档（C7）扫参定下来，扫参不重嵌
- MCP server：stdio JSON-RPC 单进程，`codebase-retrieval` 单工具，入参只有 `query`

顺序是 ANN 先、MCP 后，中间隔一道验收：ANN 可能掉分，MCP 测不出分数。

**验收**：

1. 单元测试：重建、搜索、索引与库计数不符时拒绝、递增重查的终止条件
2. **L1 报分四列并排**：grep / bm25 / vector（精确）/ ann。ann 必须打过 grep 与 bm25 两条基线
3. **附加门槛：ann 相对精确扫描的召回损失**。基线那一关已由阶段 2 的精确扫描过了，本阶段的新风险是 ANN 自己丢的召回，必须单独量
4. 接一个真 agent 上 MCP 查几个问题，人看输出

第 2 步过不了就停在那里查原因，不要往下做 MCP。

付费嵌入（阶段 2 验收 4）推到本阶段之后：扫 HNSW 参数和量化档都不重嵌，本地 0.5b 的向量够用，ANN 的召回损失也是相对精确扫描量的，与模型质量无关。$9.3 留到参数定死再花。

### 遗留到后续阶段

- **ANN 的价值在这个规模上测不出来**：零召回损失、零延迟收益（见 D24 两张表）。它是为超大仓库准备的，而超大仓库还没有向量。付费嵌入之后必须重报这两项
- **`--ef` 已删**：过取量就是搜索扩展量，要调只能调 `match/` 的递增重查阶梯（1000 / 4000 / 16000），这个阶梯本身没扫过参
- **holdout 仍未用向量那一路跑过**：阶段 1 的函数级过拟合告警还没销掉
- **MCP 只有一档**：单进程、单分支、无预算、无会话、无 `expand`。客户端/服务端拆分归阶段 7 与 10，预算与会话归阶段 6
- **`full_text = 20` 是个凑数的常数**：阶段 6 的 `token_budget` 来了就删

train 嵌入成本约 $9.3、付费档约 4.3 小时（实测，`benchmark.md` 成本节）。这份嵌入后面阶段 4–7 全部复用，不需要重付——除非改切块方案或 `max_bytes`。

## 阶段 4：混合召回（完成，2026-09-18）

设计见 D26。

- **先重构**：`match/` 的两套装配代码（词法一套、向量一套）合成一个融合器，每一路只交名次

- 权重四档扫描（0 / 0.25 / 0.5 / 1.0），扫参不重嵌、不重建索引

顺序是重构先、融合后，中间隔一道逐位比对：重构如果动了任何一条旧路线的名次，那就不是重构。

**验收**：

| redis | 43 | 0.679 / 0.431 | 0.824 / 0.548 | **0.841 / 0.576** |
| prometheus | 50 | 0.720 / 0.416 | 0.710 / 0.359 | **0.787 / 0.506** |
| tokio | 47 | 0.611 / 0.200 | 0.685 / 0.417 | **0.735 / 0.528** |
| pandas | 50 | 0.327 / 0.056 | **0.712** / 0.227 | 0.682 / **0.283** |
| netty | 29 | 0.520 / **0.300** | 0.517 / 0.269 | **0.655** / 0.269 |

**pandas 是唯一一个融合没赢的文件级**（0.682 对 ANN 0.712）。那里词法几乎不工作（0.327），它的名次仍然进了融合。这正是权重从 1.0 降到 0.5 要缓解的问题——等权时是 0.595，降权后回到 0.682，但仍到不了纯向量。**一个全局权重吃不掉「某一路在某个仓库上没用」这件事**，那要么靠查询理解（C1）、要么靠重排（阶段 5）。

**4. 重构的副作用（已报）**：统一装配后，「Chunk 名次融合它所在文件的名次」对向量那一路同样生效——阶段 3 的向量路没有这一步。文件级逐位不变，函数级四项全涨（`func_recall@50` 0.599 → 0.615）。明细见 D26。

### 遗留到后续阶段

- **权重是全局常数**：最优值按仓库不同，pandas 与 netty 的方向相反。`func_acc@10` 上等权（0.382）比 0.5（0.368）高，这一项是被权重换掉的
- **换生产模型后要重扫**：结论建立在本地 0.5b 上，两路的强弱关系变了权重就得变
- **符号那一路没权重**：阶段 7 加进来时要重扫三路
- **holdout 仍未跑过**：阶段 1 的函数级过拟合告警还挂着。留到阶段 5 重排之后一次性验，不在本阶段花
- **`func_recall@50` 增益很薄**（0.630 对 0.615）：融合赢在名次不赢在集合，集合那一头要靠重排
- MCP 默认路线仍是 `lexical`，hybrid 要显式选（D26）

本阶段零额外成本：复用阶段 3 的嵌入，扫参不重嵌、不重建索引。

## 阶段 5：重排

设计见 D27。

- `model/`：`Reranker` 类，复用 `Limiter`、重试分类与 `Post`；说 Voyage rerank API 的请求与响应形态
- `match/`：融合装配完成后调重排，文件序从重排后的 Chunk 序重新推导
- `--rerank` 正交开关（不是新路线名），默认关；重排失败硬报错，不退回融合序
- 扫参：池深 50 / 100 / 200，单文档截断三档

顺序是先接模型跑通单测、再接进 `match/`、最后扫参。中间隔一道逐位比对：开关关闭时三条旧路线的名次必须与阶段 4 完全相同。

**评测实际走 OpenRouter 上的 `voyageai/rerank-2.5-lite`**：Voyage 直连 key 没绑支付方式时限流 3 RPM / 10K TPM，单次请求就超额，一题都跑不完（实测）。OpenRouter 无此限制，$0.02/1M token，但**没有 rerank-3**，所以拿不到那 2 亿免费额度。下面这段记原计划：

**原定模型 `voyage rerank-3`**，不是 `model.md` 选定的 `jina-reranker-v3.5`——Jina key 拿不到（阶段 2 验收 4 卡的是同一件事）。Voyage 是真托管 API，2 亿免费 token 覆盖 L1（那份额度只给 rerank-3 系列，2.5 是 0），代码路径与将来接 v3.5 一致。代价是 cross-encoder 而非 listwise：200 条候选要 200 次前向，池深从此是成本旋钮。生产选型 D6 不动，见 D27。

**试点已跑（2026-09-18，tokio 单仓 47 题，池深 50）**：重排把 mrr 顶上去（func_mrr +72%），把 recall@10 拽下来（func_recall@10 −0.067），按门槛第 4 条不通过。`recall@池深` 逐位不变，不变量那一条过了。明细与两条已定结论（池深必须大于指标的 k、单文档 1000 字节是下一个要扫的参数）见 D27。

**验收仍未跑**：完整 L1 需要 5 个仓库、三组路线对照与池深 / 截断两轮扫参，按 $0.02/1M token 估约 $5–10 的调用额度。当前 key 额度 $0.10，已用 $0.073。

**验收**：

1. 单元测试：响应解析、名次重建（返回的 index 映射回 chunk）、文档截断、429 / 5xx 退避重试、候选数为 0 与 1、重排失败硬报错
2. **候选池天花板**：先报 `--route hybrid` 在池深处的 recall。重排改不了这个数，它是本阶段增益的上界，不先报它，后面的涨幅读不出剩余空间
3. **L1 六列并排**：grep / bm25 / 词法 / ann / hybrid / hybrid + 重排。另报三条路线各自的重排增量（词法、ann、hybrid 各一对），看重排补的是哪一路的短板
4. **门槛**：hybrid + 重排在 `file_mrr`、`file_ndcg@10`、`func_recall@10`、`func_acc@10`、`func_mrr` 上都不低于 hybrid——重排是名次这一头的活，集合指标不归它管；同时 `recall@池深` 必须逐位不变，变了就是重排把候选弄丢了，是 bug 不是调参
5. **holdout 第 2 次**：只跑 duckdb、vuejs 两个中等档，消耗一次配额（剩 3 次），写进 `../eval/holdout-log.md`。**跑完不许基于结果回头改任何参数。** 前置：这两个仓库要先本地嵌入，与 train 同模型、同 `max_bytes`。超大档的两个 holdout 仓库（rust、airflow）仍无向量，本次不跑，写明
6. 两条基线与词法那一行必须与阶段 2、3、4 逐位相同

第 2、4 步是这一阶段的全部意义：**重排只在候选池内部换座位**。公开数据说重排给 NDCG 带来 +68%（稀疏）到 +120%（稠密），那是别人的数字；自己的数字是阶段 1 实测的「答案文件 15% 落在 10–30 名」，那 15% 是这一阶段的靶子。

成本：Voyage 免费额度内。池深 50 时一遍 L1 约 8.8M token（219 题 × 2 组 × 50 条 × 约 400 token），扫参按遍数累加。嵌入复用阶段 3 的，不重嵌。

## 阶段 6：`curate/` 策展

**这是本项目区别于「又一个代码检索器」的地方，不是可选增强（D16）。**

- 工具契约加入 `token_budget` 和 `session_id`
- 多级保真：tree-sitter 提取签名档与引用档
- 单次调用内去冗（三路召回的重复、方法与所属类的重叠）
- MMR 多样性约束
- 预算约束下的贪心组装
- 会话级去冗（策略见 D17）

前置要求：`match/` 的输出量要为本层留出选择空间，`match/` 交出约 200 条而非 5 条。

验收走 `benchmark.md` 的 **L3 预算曲线**：固定 L1 Recall@10 达标，测 Context Package 的实际 token 数，扫 2K / 4K / 8K / 16K / 无限。

**在哪个预算点达到无限预算档的质量，那个点越低本层越有效。**

不是 Recall@10。Augment 在这一层拿到的是 token 少 32%、准确率打平——赢的是单位 token 的信息密度，不是召回。

本阶段零额外成本，复用阶段 3 的嵌入。
