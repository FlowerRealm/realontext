# 未决问题与待研究

本文件记录**已知自己不知道**的事，包括设计过程中被跳过、被搁置、或被判断为「营销话术」而未深究的内容。

留在这里的原因：不知道怎么做不等于不存在。跳过会让它们在实现阶段以 bug 的形式回来。

状态标记：

- **阻塞** — 影响架构，实现前必须有答案
- **待研究** — 需要调查，不阻塞当前阶段
- **已知缺口** — 明确接受的取舍，记录以防遗忘

---

## A. 知识库层

### A1. 计数器的信号从哪来（阻塞）

ACE 论文的条目带 `helpful` / `harmful` 计数器，靠它淘汰坏条目。

但 **agent 不会主动反馈「这条有用」**。论文的实验环境有明确的任务成功信号（AppWorld 的任务通过、Finance 的答案正确），本项目没有。

候选信号源，都未验证：

- agent 在收到某条目后是否继续追问同一主题（追问 = 条目没解决问题）
- 检索返回的代码是否最终出现在 commit 里
- agent 是否显式调用 `expand` 要回原文（要回 = 蒸馏版不够）
- 人工反馈接口

**这是知识库层最大的未知。** 没有信号，grow-and-refine 退化成只 grow 不 refine，坏条目永久累积。

### A2. Reflector 的触发条件（阻塞）

每次会话结束？累积 N 次检索？定时？

影响成本（每次触发都是模型调用）和知识库的新鲜度。论文未给出通用建议。

### A3. 条目粒度（待研究）

一条 bullet 该多大？一句话？一段？

太细则条目爆炸且检索噪音大；太粗则失去「可独立寻址、可增量更新」的前提。

### A4. 错误条目的纠正入口（阻塞）

知识库存在服务端、自动累积、条目数到千级（`modules/playbook.md`）。

**一条错误条目会被嵌入并永久参与检索。** 目前没有设计任何人工审阅或纠正的入口。

需要至少：导出、搜索、删除、置顶/封禁。

### A5. 冷启动（待研究）

新接入的仓库知识库为空。需要多少次会话才能积累到有价值的程度？

在此之前，知识库层是纯成本无收益。可能需要一个 bootstrap 路径——例如从 commit 历史批量提炼初始条目。

### A6. 知识库中毒（待研究）

agent 的错误推理被 Reflector 提炼成条目后，会反过来污染后续检索，形成自我强化的错误。

论文的计数器机制理论上能纠正，但依赖 A1 的信号。

## B. Augment 宣称但本项目未建模的数据源

以下是 Augment Context Engine 官方列出的索引对象。前面的设计只覆盖了代码和 commit 历史，其余被跳过。

### B1. Tribal knowledge（待研究）

Augment 反复使用这个词，但从未定义。

可能指：PR review 讨论、issue 里的设计争论、Slack/邮件里的口头约定、离职同事留下的注释。

**完全没有调查过这个词的实际所指。** 需要看他们的文档或实际产品行为。

### B2. 外部文档与 issue（待研究）

Augment 索引 external docs 和 tickets。

本项目当前只索引代码和 commit。issue/PR 正文其实可以从 GitHub API 免费拿到，是最低成本的扩展方向。

### B3. 风格指南与 codebase patterns（待研究）

「这个仓库的错误处理惯例是什么」这类问题，靠向量检索代码片段回答不了。

可能是知识库层的一个条目类别，而不是独立数据源。

### B4. "Context signal optimization that maintains relevance across session duration"（待研究）

Augment 产品页的原话，前面引用过但从未设计。

字面意思是：同一会话内，早期提供的上下文相关性会衰减，需要跟踪。知识库层解决了「重复」，但没解决「衰减」。

### B5. "+70% 提升"宣称（待研究）

Augment 称把 Context Engine 挂到 Claude Code / Cursor / Codex 上带来 70%+ 的性能提升。

前面判断为营销数字直接略过，**没有查过它测的是什么**。如果口径合理，它是本项目最直接的对标指标。

## C. 检索链路中未决的设计

### C1. 查询理解（阻塞）

**整条链路从未建模查询侧的处理。**

agent 传来的是自然语言任务描述，直接拿去做嵌入和 BM25。但：

- 要不要做查询改写 / 扩展？
- 要不要拆成子查询分别召回？
- HyDE（先让模型生成假想答案再嵌入）值不值得？

BM25 尤其受影响——自然语言描述里的词和代码里的标识符往往对不上。

这是 `match/` 之前的一层，目前完全空白。

### C2. 多路融合方法（阻塞）

向量、BM25、符号三路结果怎么合并成一个排序？

RRF（Reciprocal Rank Fusion）是默认选择，但权重怎么定、要不要按查询类型动态调整，都没决定。

### C3. `curate/` 的评价指标（已解决）

原问题：「相同 Recall 下的 token 用量」不是一个可直接测量的指标。

**已解决**：`benchmark.md` 的 **L3** 给出了操作化协议——固定 L1 Recall@10 / L2 Recall@50 达标，测 Context Package 的实际 token 数，扫 2K / 4K / 8K / 16K / 无限的预算曲线。验收标准是「在哪个预算点达到无限预算档的质量」，那个点越低越有效。

**遗留**：这个协议是自定义的，没有第二个系统用同样的口径跑过，所以只能纵向比自己，无法横向比别人。

### C4. MMR 参数（待研究）

多样性与相关性的权衡系数未定。

### C5. HNSW 参数（已解决）

`M = 16`、`efConstruction = 128`（D24 实测）。

**`efSearch` 不是独立旋钮**：usearch 用 `max(efSearch, wanted)` 搜索，而 `wanted` 是 `match/` 的过取量（起步 1000），任何低于过取量的 `efSearch` 完全不起作用。过取量就是搜索扩展量。

在 3 个中等仓库上，f32 索引对精确扫描的 top-10 一致度恒为 1.000，M 与 `efConstruction` 怎么取都一样。**遗留**：这三个仓库只有 2–6.7 万向量，过取 1000 已经是语料的 1.5–5%，近似几乎退化成精确。超大仓库（30 万–140 万块）没有向量，那个规模上的召回损失未测。

### C6. Chunk 尺寸目标（已解决）

「合并兄弟节点直到填满嵌入窗口」——但嵌入窗口是 32K，把 32K 塞进一个 chunk 显然是错的。

**已解决**（D21、D22）：切块按函数 / 容器，不设尺寸目标；嵌入输入按字节截断到 `max_bytes`，截断上限进指纹。

`max_bytes` 取 16384：redis 上 8 KB 掉分、32 KB 无收益，其余仓库不敏感。扫参数据见 D22。

### C7. 量化档位（已解决）

`store/` 落盘 fp32（D22），`vector/` 索引也取 **f32**（D24 实测）。

i8 索引小 3.2–3.6 倍、建索引快一倍，`recall@10` 几乎不变（0.711 对 0.702），但**名次指标掉 9–16%**（file_mrr 0.451 对 0.533）。量化重洗了近似并列的候选，集合指标看不出来，名次指标看得很清楚——而 `curate/`（阶段 6）在预算内只装得下前几条，吃的正是名次。

**遗留**：这个权衡只在 6.7 万向量以下测过。生产规模（140 万块 × 1024 维）f32 索引约 5.6 GB、i8 约 1.4 GB，装不装得下会改变结论，到时重测。

## D. eval 的方法论问题

主标准是**自建测试集**（D20），不是公开基准。三条铁律与完整方法见 `benchmark.md`，仓库名单见 `../eval/repos.txt`。

### D1. ground truth 与索引内容循环（已解决）

原方案用 commit message 当 query、patch 文件当答案，而 commit 历史同时被索引，构成数据泄漏。

**已解决**：铁律二——语料锚定在 PR 的 base commit 状态，修复之后的代码、提交、注释都不在语料里。开启提交摘要后（阶段 9），commit 历史同样截断在 base commit 之前。

### D2. 基线的公平性（已解决）

原担心 commit message 对 grep 不友好导致高估。

**已解决**：铁律一——query 用 issue 正文，修复之前写的，由不知道答案的人写。

**额外加了一条监控**：每次报分必须同时报「query 里直接出现 ground truth 文件路径或函数名的比例」。真实 issue 有时确实会写出标识符，这是真实分布的一部分，不该剔除；但这个比例一高，测试集就退化成字符串匹配任务，BM25 会虚高。它是测试集难度的体温计。

### D3. 测试集的语言偏向（已解决）

公开基准（CORE-Bench、LocBench、SWE-bench 系列）**以 Python 为主**，测不出 C / C++ / Go / Rust / Java / TypeScript 上的表现。

**已解决**：自建测试集七种语言权重相同，每种两个仓库（一个超大、一个中等），名单冻结在 `../eval/repos.txt`。

**这是放弃公开基准换到的最大收益。** 语言分布由自己决定，不受别人的数据集构成约束。

### D4. 全分支能力无基准（已解决）

索引全部分支（D14）是本项目的差异化之一，但所有公开基准都是单一 checkout 状态。

**已解决**：`benchmark.md` 的全分支测试。利用「一个 PR 在 merge 之前，它的代码只存在于非默认分支」这个时间性质，复用 L1 的 issue 正文当 query，对照组只索引默认分支、召回必然为 0。场景是**重复劳动检测**。

**遗留**：指标是二元的（召回到 / 没召回到），只能证明能力存在，不能证明能力好。

### D5. API-only 无法微调（结构性劣势）

公开数据（CORE-Bench）显示 in-domain 微调把 issue-to-edit 定位的 NDCG@10 从 20.3 拉到 32.8，**收益接近翻倍**。

本项目 API-only（D5 决策），无法微调 Provider 的模型。这个差距必须靠 `match/` 的多路召回与重排、`curate/` 的策展补回来。

放弃公开基准后**这个差距无法直接量化**——没有微调模型的对照组。只能观察自建测试集上相对 ripgrep / BM25 / 纯向量三条基线的增益够不够大。

### D6. 自建测试集出卷答题同源（已知缺口）

query 的选取规则、ground truth 的定义、参数的调整，全部在同一个人手里。这是自建评测的结构性风险。

补偿措施三条，见 `benchmark.md`「防自欺的硬规则」：

- 测试集冻结进 git，改一次记一次
- 14 个仓库里 4 个划为 holdout，调参期间不许看
- 每次报分必须同时报 ripgrep 与 BM25 两条免费基线——它们不碰本项目任何代码路径，调参时调不动

**不能完全消除。** 分数涨而基线同步涨，说明测试集变简单了，不是系统变好了。

## F. 规模上限未建模（待研究）

当前所有估算基于 10 万文件量级。百万文件以上的仓库（Chromium、Linux、大型 monorepo）会在哪一环先撑不住，没有分析过。

候选瓶颈：HNSW 内存、首次嵌入费用、language server 启动时间、bare mirror 磁盘。
